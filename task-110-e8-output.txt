2. VERIFIED INVARIANTS

- LONG_TERM_RENTAL and SHORT_TERM_RENTAL remain distinct.
- Long-term Occupancy has Lease provenance; short-term Occupancy has Stay/Booking provenance.
- ENTRY is required before Occupancy start; EXIT is required before end/checkout.
- Planned arrival/departure are not overwritten by actual check-in/check-out.
- Exact starts, inspections and turnover commands converge; changed replay conflicts.
- One Stay per Booking and one Occupancy per Lease/Stay are database enforced.
- Cross-tenant reads behave as not found and writes remain RLS protected.
- Availability intervals and cleaning blocks remain UTC half-open.
- Short-term checkout releases its Booking claim before installing the cleaning claim.
- Condition evidence is private and absent from public availability/catalog routes.
- Billing, Property Management and Maintenance ownership boundaries remain intact.

3. BLOCKING GAPS

- Long-term Occupancy end changes lifecycle state but does not transactionally release the Lease
  RentalAllocation and rental_allocation_claims. The required operational closure is incomplete.
- Long-term `REMOVE_FROM_RENTAL_CATALOG` is still derived from an active long-term allocation rather
  than an effective active Occupancy. A prepared Lease can therefore remove a target too early, and
  a closed Occupancy can remain excluded while its allocation stays active.
- Lifecycle commands do not publish the declared domain events through the repository event/outbox
  convention. Constants exist, but no facts are emitted transactionally.
- Cancellation, no-show, early termination, extension, renewal and controlled overstay states are
  specified but have no application commands, persistence transitions, API or tests.
- There is no separate Lease operationalization command/API; current execution assumes a Lease and
  allocation already exist and starts Occupancy directly after ENTRY.
- The operational collection does not include inspections, active OperationalBlocks, cleaning state,
  next availability or completed/recent operation summaries required by E6/E7.
- Web does not provide the required dedicated views for pending cleaning, operational blocks, next
  availability and recent completed operations. It also does not integrate an operational summary
  into Property Workspace.
- Cleaning delay cannot extend an existing active cleaning block through a dedicated lifecycle
  command; only its initial expected end and final release are implemented.
- Maintenance discovered at EXIT is recordable as damage/observation, but no adapter command/event
  boundary creates or retains a MAINTENANCE block from that fact.

4. TECHNICAL DEBT / RESIDUAL RISKS

- Operational list query currently materializes capabilities in PostgreSQL repository code; these
  should be consolidated with domain policy tests as exceptional transitions are added.
- Client-generated command entity IDs make mutation replay dependent on the caller retaining its
  identifiers. A canonical Idempotency-Key command ledger would improve HTTP retry semantics.
- Evidence references are syntactically validated but not resolved through a media/document port.
- API HTTP coverage validates authentication, validation and tenant authority forwarding, while
  dedicated tests for every command's 403/404/409 mapping remain incomplete.
- The repository emits pg@8 deprecation warnings in concurrency tests because the test deliberately
  overlaps commands; tests pass, but the eventual pg@9 migration should be reviewed.
- Web production build emits the pre-existing >500 kB chunk advisory.

5. DEFERRED CAPABILITIES

- Financial charges, deposits, invoices and accounting remain deferred to Billing.
- Maintenance work-order execution remains deferred to a Maintenance bounded context.
- Binary media storage, signature capture and document lifecycle remain external capabilities.
- Workforce/housekeeping scheduling is intentionally not implemented.
